# 06. Accessibility

## 1. The standard we commit to

**Baseline: WCAG 2.2 Level AA**, for every workflow a reviewer, operator or manager can reach in the app. This satisfies PRD `docs/product-requirements/PRD.md:723`, "Target WCAG 2.2 AA, or the museum's stricter applicable standard," and its two follow-on rules at `PRD.md:724-726`: keyboard access, visible focus, semantic labels, adequate contrast, non-color-only status, scalable text, screen-reader-compatible forms/tables, reduced motion, and "Never encode transcript disagreement only through color; include text and symbols."

Full AA reference: https://www.w3.org/WAI/WCAG22/quickref/?levels=aa

### The seven criteria new in 2.2 that this app must pass

Confirmed against the quick reference (https://www.w3.org/WAI/WCAG22/quickref/):

| SC | Level | Requirement | Where it bites this app |
|---|---|---|---|
| 2.4.11 Focus Not Obscured (Minimum) | AA | A focused control must not be entirely hidden by other author content (banners, sticky bars). | The environment banner (`workspace.dart:604-612`) and the error `MaterialBanner` (`workspace.dart:665-675`) sit above the body; a focused item scrolled underneath them must not be fully covered. |
| 2.4.13 Focus Appearance | AA | The focus indicator has a contrast ratio of at least 3:1 against adjacent colors and covers an area at least as large as a 2px-thick border around the component. | Default Material focus rings on `IconButton`/`TextButton` pass this out of the box; the hand-rolled region overlay (`workbench.dart:532-563`) uses a bare `InkWell` with no explicit focus decoration, drawn over a busy photograph where the default focus highlight can be lost against similar-toned pixels. |
| 2.5.7 Dragging Movements | AA | Any drag-only interaction needs a single-pointer alternative. | Not yet triggered: region editing today is numeric fields, not drag handles (`region_editor.dart:160-189`). Flag for the redesign: if drag-to-resize handles are added to the region editor or the `InteractiveViewer`, the numeric-field editor must be kept as the pointer-free alternative, not removed. |
| 2.5.8 Target Size (Minimum) | AA | Pointer targets are at least 24x24 CSS px, unless inline or the target has an equivalent that meets the size. | `ChoiceChip` (32dp tall) passes. The region overlay boxes (`workbench.dart:521-531`) are sized directly from the label's bounding box scaled to the display width; a small pinned-insect label can produce a target well under 24x24. |
| 3.2.6 Consistent Help | A | A help/contact mechanism, if present, stays in the same relative place across pages. | No help mechanism exists today. Not a current violation, but if the redesign adds one (e.g., a help icon in the app bar), it must appear at the same position on Queue, Intake and Workbench. |
| 3.3.7 Redundant Entry | A | Information the user already supplied in this process must not be re-requested, unless re-entry is essential. | The magic-link email field remembers the last entered address (`magic_link.dart:78-97`) and dialogs pre-fill from the current field/observation state (`workbench.dart:101-113`). Keep this pattern; do not add a dialog that re-asks for data the record already holds. |
| 3.3.8 / 3.3.9 Accessible Authentication | AA / AAA | Sign-in must not rely solely on a cognitive function test (remembering a password, solving a puzzle) unless an alternative or object recognition/personal-content exception applies. | The magic-link flow (`magic_link_screen.dart`) already satisfies this: no password, a link plus optional email re-entry. The synthetic-fixture password path (`auth.dart:230-247`) is fine because it is development-only and never reaches museum staff. |

### Platform expectations

| Surface | What "AA" means in practice | Primary reference |
|---|---|---|
| iOS / iPadOS | VoiceOver reads every control with an accurate role, label, value and state; Switch Control can reach and activate every action; Voice Control labels ("tap Confirm label coverage") match visible text; Dynamic Type up to at least the "AX5" / 200% equivalent does not clip content. | https://developer.apple.com/design/human-interface-guidelines/accessibility |
| Android | TalkBack announces role, label and state for every control; touch targets are at least 48x48dp; content descriptions exist on every icon-only control; system font scale up to 200% (Settings > Display > Font size, "Largest") does not clip content. | https://developer.android.com/guide/topics/ui/accessibility/principles |
| Web (desktop Chrome, the reviewer's likely browser per the brief) | Every action is reachable and operable from the keyboard alone, in a sensible order, with a visible focus indicator meeting SC 2.4.13; no keyboard trap. | https://docs.flutter.dev/ui/accessibility-and-internationalization/accessibility |
| All platforms | Respect the user's reduced motion, high contrast and reduced transparency settings via `MediaQuery.disableAnimationsOf(context)`, `MediaQuery.highContrastOf(context)` and the platform's own transparency setting (no custom blur/glass effects to begin with, per the brief's ban on glassmorphism). | https://api.flutter.dev/flutter/widgets/MediaQuery-class.html |

Flutter's own accessibility guidance (https://docs.flutter.dev/ui/accessibility-and-internationalization/accessibility) states the framework-level bar this app should clear before shipping any screen: every interactive element performs a real action, all controls are intelligible under TalkBack and VoiceOver, contrast is at least 4.5:1, tappable targets are at least 48x48 px, and the UI stays legible at large text-scale factors.

### 2.2 Gaps, ranked by impact

**P0 (blocks a screen-reader or keyboard-only user from completing the review task):**

1. **The reading diff is entirely a visual/typographic signal.** `workbench.dart:656-679` builds the per-character diff with `TextDecoration.underline`, `FontWeight.w700` and `backgroundColor: Color(0xffffe7a3)` on individual `TextSpan`s. None of `TextDecoration`, `FontWeight` or `backgroundColor` are exposed through the Flutter semantics tree, and `Text.rich` collapses all of its `TextSpan` children into a single semantics node carrying only the concatenated plain text (https://api.flutter.dev/flutter/widgets/Semantics-class.html, "container"/merging behavior). A VoiceOver or TalkBack user hears the literal reading and nothing else: no indication that it differs from the reference reading, where, or by how much. This directly violates PRD `PRD.md:726`, "Never encode transcript disagreement only through color; include text and symbols," because today it is encoded only through style, which is equivalent to color for a non-visual user. Above 4000 runes (`workbench.dart:659-660`) the diff styling is dropped entirely even for sighted users.
2. **No semantic list alternative to the on-image region overlays for screen-reader and switch-control users to *understand which regions exist*, only to select one.** `workbench.dart:512-567` draws each region as a `Positioned` `Semantics(label: 'Label region ${r['region_id']}', button: true)` box on top of the photograph. `region_id` is an opaque server identifier (for example `"reg_3f9a"`), not a description, so the label itself is not meaningful. There *is* a duplicate `ChoiceChip` list (`workbench.dart:577-594`, "Label 1," "Label 2," ...) that lets a screen-reader user select a region without hunting for a tiny box on an image, which is good, but the overlay's own label should match it ("Label 2") instead of the raw ID, and the two lists currently drift: the chip numbers regions by their position in `specimen.regions`, the overlay's spoken label does not.
3. **Disabled actions never say why they are disabled.** Every gating condition in the app is a bare `null` passed to `onPressed`: `_blocked('coverage')`, `_blocked('approve')`, `_blocked('classification')`, `_retryBlocked`, `_blocked('regions')`, `_blocked('transcription')`, `_blocked('field')` (`workbench.dart:1016-1107, 602-615, 852-863, 916-929`), and the run-control buttons in `operational_panel.dart:162-174`. A sighted mouse user can sometimes infer the reason from surrounding text; a screen-reader user tabbing to "Confirm label coverage" hears "Confirm label coverage, button, disabled" with no reason, which is exactly the case the brief calls out: "the app disables actions the server does not permit, and a user gets no reason." This is also a WCAG 3.3.1/4.1.2 concern (name, role, *state* must be programmatically determinable, and state alone without a reason is not enough for a scientist deciding what to do next).
4. **`RegionEditor` has no accessibility support at all.** `region_editor.dart` (318 lines) contains zero `Semantics`, zero `liveRegion`, and its only `SourcePixels` call has a semantic label. The four numeric fields (`Left x`, `Top y`, `Right x`, `Bottom y`, lines 160-189) share one combined error string (`_visibleError`, lines 29-33) rendered as plain `Text` with no `liveRegion` (line 263-267) and no per-field `errorText`, so a screen-reader user who mistypes a coordinate gets no spoken feedback at all, and even a sighted user cannot tell *which* of the four fields is invalid, only that something is.
5. **Dialogs never set an initial focus or return focus to the control that opened them.** None of the eleven `showDialog<Json>` / `showDialog<String>` call sites in this app (`workbench.dart:116, 326, 337`, `operational_panel.dart:23`, `evidence_panel.dart:88`, `review_context.dart:195` `ClassificationDialog`, `region_editor.dart` (`RegionEditor` itself is the dialog), `search_filters.dart` (`SearchFilters`), `reading_declarations.dart:209` (`ReadingDeclarationDialog`)) sets `autofocus: true` on any field, heading, or the primary action. Flutter's default dialog focus behavior places focus on the first focusable descendant in tree order, which in an `AlertDialog` is frequently the first form field or, worse, is not deterministic once a `DropdownButtonFormField` is present before it. None of them explicitly restore focus to the invoking button when the dialog closes.

**P1 (a real barrier or serious annoyance, not a hard blocker):**

6. **Touch targets on the region overlay can fall under the 24x24 CSS px WCAG 2.2 minimum (SC 2.5.8) and well under the 48x48 platform recommendation.** The overlay box size is derived directly from the label's `bbox` scaled into display pixels (`workbench.dart:521-531`); a small pinned-insect label photographed at typical resolution can produce an overlay a handful of device-independent pixels on a side. The `ChoiceChip` alternative (32dp tall, comfortably over 24px) is the only reliable target today.
7. **`ChoiceChip` used as a tab bar carries no tab semantics.** The "Readings / Fields & evidence / History" switcher (`workbench.dart:1118-1130`) and the region editor's "Label 1 / Label 2 / ..." switcher (`region_editor.dart:79-90`) are each a `Wrap` of independent `ChoiceChip`s. Flutter's semantics for a selectable chip expose `selected` state on a button-like node, not a `tab` role inside a `tablist`; there is no `SemanticsRole.tab` set anywhere in this codebase (`grep -rn "SemanticsRole" lib/` returns nothing). A screen-reader user hears a sequence of separately-focusable toggle buttons rather than "tab 1 of 3, selected," and there is no arrow-key roving-tabindex behavior for a keyboard user, unlike a real `TabBar`.
8. **`large_record.dart:157-167` collapses an entire 12,000-character evidence page into one semantics label and explicitly hides its own selectable text from the tree.** `Semantics(container: true, label: pageText, excludeSemantics: true, child: SizedBox(height: 320, child: SingleChildScrollView(child: SelectionArea(child: Text(pageText)))))`. This is a deliberate, well-intentioned choice (avoid flooding the tree with per-character semantics from a long JSON dump) but it is the wrong fix: `excludeSemantics: true` throws away the ordinary paragraph/line semantics that `Text` already provides for free, replacing structured, navigable content with one flat announcement that a screen reader will read start-to-finish with no way to jump by line or word. `SelectionArea`'s own selection affordance is also excluded. The visible `SizedBox(height: 320)` itself is fine, since it already scrolls internally (`SingleChildScrollView`) and does not clip at any text scale.
9. **Two fixed-height, non-scrolling fallback messages can visually overflow at 200% text scale.** `workbench.dart:452-460` (`Container(height: 380, ...)`, "Preview unavailable. Refresh to renew source access.") and the `errorBuilder` in `source_pixels.dart:25-27` ("Source preview unavailable. Refresh to retry.") both center a `Text` inside a fixed-height `Container` with the default `clipBehavior: Clip.none`. At large text scale this string can require more than one line of a much taller font, and `Container` does not clip or scroll its child, so the message paints past the box boundary and overlaps the zoom/rotate controls above it. This is the one real "fixed-height container" defect in the app; the other two named in the brief (the 320px text box above, and the region editor's 180px preview box at `region_editor.dart:95-145`) do not have this problem, because the 320px box scrolls and the 180px box holds only an image and a positioned border, no unbounded text.
10. **`ExpansionTile` state (expanded/collapsed) is not confirmed to reach assistive technology.** Every field, evidence phase, authority result and audit event in the review workbench is an `ExpansionTile` (`workbench.dart:742-749,834-849,892-935`, `evidence_panel.dart` phase cards, `audit_history.dart:125-158`, `risk_assessment.dart:49-65`). Flutter exposes an `expanded` boolean through `SemanticsProperties`, but nothing in this codebase sets it explicitly, and whether the stock `ExpansionTile` widget sets it internally needs to be confirmed with a semantics-tree dump (test method in section 4.1), not assumed.
11. **Queue list items have no stable widget key.** `workspace.dart:413-440` builds `_items.map((s) => Card(...))` with no `key: ValueKey(s.id)`. The 20-second poll (`workspace.dart:60-70`) replaces `_items` on every quiet refresh; without a key, Flutter's element reconciliation matches by position, not identity, so if the server ever returns the list in a different order between polls (a sort tie-break flip, a new record inserted at the top), a keyboard or screen-reader user's current position/focus can silently jump to a different specimen mid-read.

**P2 (worth fixing, lower risk today):**

12. No screen in the app reads `MediaQuery.disableAnimationsOf(context)`, `MediaQuery.highContrastOf(context)` or `MediaQuery.boldTextOf(context)` (confirmed by `grep -rn "MediaQuery" lib/`, zero results). Low risk today because the app uses only stock Material transitions and no custom motion, but any motion added in the redesign (page transitions, `AnimatedSwitcher` between tabs, a custom loading skeleton) must gate its duration/existence behind `disableAnimations`.
13. Skeleton/loading states are ad hoc `CircularProgressIndicator()`/`LinearProgressIndicator()` calls without a consistent policy for whether they should be hidden from or exposed to the semantics tree; `main.dart:45` (`email_link_browser.dart` initial gate) shows a bare `CircularProgressIndicator()` with no semantics label at all, unlike the two `LinearProgressIndicator`s that do carry one.

### 2.3 Color contrast, computed

Scaffold background is `0xfff4f6f3` (`main.dart:107`). Using the WCAG relative-luminance formula (https://www.w3.org/WAI/WCAG22/quickref/#contrast-minimum):

| Foreground | Hex | Used for | Contrast on `#F4F6F3` | AA text (4.5:1) | AA large text / non-text (3:1) |
|---|---|---|---|---|---|
| Cleared disposition | `#14513D` | List icon, `workspace.dart:303,420-424` | **8.5 : 1** | Pass | Pass |
| Needs human review disposition | `#754300` | List icon | **7.5 : 1** | Pass | Pass |
| Deferred disposition | `#594D7C` | List icon | **7.0 : 1** | Pass | Pass |
| Default/unknown disposition | `#374B60` | List icon | **8.3 : 1** | Pass | Pass |
| Environment-banner text | `#483500` | on banner background `#FFE7A3` (`workspace.dart:606-610`) | **9.6 : 1** | Pass | Pass |

All four disposition colors already clear AA comfortably, even though today they are used only decoratively on a leading `Icon` (`workspace.dart:420-424`), never as text. That means the palette is already safe to promote to a filled status chip's *text* color, not just its icon tint, once the redesign adds one (see requirement 3.1 below). The diff-highlight background `#FFE7A3` against the app's default (near-black) body text is roughly **14 : 1**, so the existing highlight passes contrast; its problem (finding 1 above) is that it is invisible to assistive technology, not that it is low-contrast for sighted users.

The default body-text color is not a literal in the codebase: `ColorScheme.fromSeed(seedColor: 0xff174f3b, surface: 0xfff9fbf7)` (`main.dart:108-111`) computes `onSurface` algorithmically at runtime. Do not hand-verify this by eye; add the contrast unit test in section 4.1, which reads the actual `ThemeData.colorScheme.onSurface` value and asserts the ratio, so a future seed-color change cannot silently regress contrast.

## 3. Requirements for the redesign

Organized by the four WCAG principles. Each row names the Flutter mechanism to use and how to verify it.

### 3.1 Perceivable

| Requirement | Flutter mechanism | Test method |
|---|---|---|
| Every pointer target is at least 24x24 CSS px (WCAG 2.2 SC 2.5.8), and at least 48x48dp on Android / 44x44pt on iOS where the platform convention applies. | Give the region overlay a minimum hit area independent of the label's true bounding box: wrap the `Positioned` overlay's child in a `ConstrainedBox(constraints: BoxConstraints(minWidth: 44, minHeight: 44))` centered on the true box, so the visible border stays accurate but the tap/focus target is never smaller than 44 logical pixels. ## 4. Testing plan

### 4.1 Automated

**Guideline matchers**, using `flutter_test`'s built-in `AccessibilityGuideline`s (https://api.flutter.dev/flutter/flutter_test/AccessibilityGuideline-class.html):

```dart
testWidgets('Workbench meets tap target and label guidelines', (tester) async {
  final handle = tester.ensureSemantics();
  await tester.pumpWidget(buildWorkbenchHarness());
  await expectLater(tester, meetsGuideline(androidTapTargetGuideline)); // >= 48x48
  await expectLater(tester, meetsGuideline(iOSTapTargetGuideline));     // >= 44x44
  await expectLater(tester, meetsGuideline(labeledTapTargetGuideline)); // every tappable node has a label
  await expectLater(tester, meetsGuideline(textContrastGuideline));    // >= 4.5:1 (3:1 large text)
  handle.dispose();
});
```

Run this for the Queue, Intake, Workbench (each of the three tabs), Region editor, and every dialog. Add it to CI as a required check (`flutter test test/accessibility/`), not an optional/manual pass.

**Golden tests at two text scales.** Wrap the harness in `MediaQuery(data: MediaQuery.of(context).copyWith(textScaler: TextScaler.linear(2.0)), child: ...)` and capture a golden image alongside the existing 1.0-scale golden for every screen; a visual diff reviewer catches the class of bug found in section 2.2, finding 9 (fixed-height container overflow) automatically, because the overflowing text will visibly clip or overlap in the 2.0 golden.

**Contrast unit test on the actual runtime token values**, not hand-computed hex pairs, since `onSurface` is generated by `ColorScheme.fromSeed` (finding in section 2.3):

```dart
test('disposition colors meet 4.5:1 against the scaffold background', () {
  final scaffold = const Color(0xfff4f6f3);
  for (final color in [0xff14513d, 0xff754300, 0xff594d7c, 0xff374b60].map(Color.new)) {
    expect(contrastRatio(color, scaffold), greaterThanOrEqualTo(4.5));
  }
});

test('default body text meets 4.5:1 against the scaffold background', () {
  final theme = ThemeData(useMaterial3: true, colorScheme: ColorScheme.fromSeed(seedColor: const Color(0xff174f3b), surface: const Color(0xfff9fbf7)));
  expect(contrastRatio(theme.colorScheme.onSurface, const Color(0xfff4f6f3)), greaterThanOrEqualTo(4.5));
});
```

where `contrastRatio` implements the WCAG relative-luminance formula (https://www.w3.org/WAI/WCAG22/quickref/#contrast-minimum) directly, so this test is the source of truth, not the manual estimate in section 2.3.

**Semantics-tree dump test per screen**, using `tester.getSemantics(find.byType(...))` or `debugDumpSemanticsTree()` compared against a checked-in text fixture, one per screen (Queue, Intake, each Workbench tab, Region editor, every dialog). This is what confirms, rather than assumes, the `ExpansionTile` `expanded` state (section 3.4), the `TabBar` `tablist` role (section 3.2), and that `large_record.dart`'s evidence page exposes real text (section 3.1) instead of a synthetic label.

### 4.2 Manual

**VoiceOver script, iPad, review flow (Workbench):**
1. Turn on VoiceOver (Settings > Accessibility > VoiceOver). Open a specimen from the queue.
2. Swipe right through the header, source image region, and each region overlay. Confirm each region announces "Label 1, button" (not a raw region ID), and that swiping through the `ChoiceChip` row announces the same numbering.
3. Double-tap a region with a known reading disagreement. Confirm VoiceOver announces the diff summary sentence before the raw text (section 3.1), not just the raw text.
4. Navigate to a disabled action (e.g., "Confirm label coverage" while blocked). Confirm VoiceOver announces the reason, not just "dimmed button."
5. Open "Correct label regions." Confirm VoiceOver's initial focus lands on a sensible first field, not silently on "Cancel." Enter a non-numeric character in a coordinate field; confirm the specific field's error is announced once. Close the dialog; confirm VoiceOver focus returns to the "Correct label regions" button.
6. Swipe through the "Readings / Fields & evidence / History" switcher. Confirm VoiceOver announces "tab, 1 of 3, selected," and that a two-finger rotor gesture can jump between tabs.
7. Trigger a save (e.g., "Record review approval"). Confirm VoiceOver announces the result once, not zero or twice.

**TalkBack script, Android tablet, same review flow:** repeat steps 1-7 with TalkBack (Settings > Accessibility > TalkBack), substituting TalkBack's swipe/double-tap gestures and its reading-controls menu for VoiceOver's rotor. Pay particular attention to step 4 and step 6, since Android's default `ChoiceChip` and disabled-button announcements differ slightly in wording from iOS's.

**Keyboard-only script, Chrome (desktop web):**
1. Load the app with a mouse disconnected (or DevTools' "emulate focused page without mouse" workflow). Tab from the app bar through the collection dropdown, the queue search field, filter chips, and into the first specimen card. Confirm a visible focus ring is present at every stop and never fully hidden under the environment banner (SC 2.4.11).
2. Press Enter/Space to open a specimen. Tab through the source-image controls (rotate, zoom, reset), each region overlay, and the region `ChoiceChip` list. Confirm every control is reachable in a logical order and none require a mouse.
3. Tab into the "Readings / Fields & evidence / History" switcher; confirm arrow keys move between tabs once migrated to `TabBar` (section 3.2), matching native browser tab-widget behavior.
4. Tab to "Correct label regions," press Enter, and confirm focus lands inside the dialog and cannot Tab out to the page behind it (no keyboard trap escape other than the dialog's own Cancel/Save or Escape).
5. Complete a field correction entirely by keyboard, including the evidence-state dropdown, and confirm the save button is reachable and its result is read out by the OS's own accessibility APIs (Chrome + ChromeVox, or Chrome + NVDA on Windows, since Flutter web renders its own accessibility tree via the DOM semantics backend).

### 4.3 CI acceptance gate

A pull request that touches any file under `lib/` may not merge unless:
- `flutter test test/accessibility/` (the guideline-matcher suite, section 4.1) passes with zero failures.
- The contrast unit test suite passes for every color token touched by the diff.
- Any screen whose visible text or structure changed has an updated, reviewed semantics-tree golden fixture in the same PR (a stale fixture fails the diff, forcing a human to look at what changed).
- Any new or changed `showDialog` call site has a matching "initial focus set, focus returned" widget test (section 3.2).
- Any new disabled `onPressed: null` branch has a matching `Tooltip`/`Semantics.hint` and a widget test asserting it is non-empty (section 3.2).

## 5. Pre-PR checklist

Run before opening any UI pull request:

- [ ] Every new icon-only button has a `Tooltip` with real, specific text (not "Action" or the icon's name).
- [ ] Every new disabled `onPressed: null` has a `Tooltip`/`Semantics.hint` explaining the exact reason, in a full sentence.
- [ ] Every new or changed status indicator shows text or a symbol, not color alone.
- [ ] Every new `showDialog` sets `autofocus` on a sensible first field or the primary action, and focus visibly returns to the invoking control on close.
- [ ] Every new fixed-size `Container`/`SizedBox` that can hold text either scrolls internally or has no unbounded text child; verify by pumping the widget at `TextScaler.linear(2.0)` and looking for clipped or overlapping text.
- [ ] Every new tappable area is at least 44x44 logical pixels; run `androidTapTargetGuideline` and `iOSTapTargetGuideline` locally before pushing.
- [ ] Every new error, warning or save-confirmation message uses the existing `Semantics(liveRegion: true)` pattern, or `SemanticsService.sendAnnouncement` (never the deprecated `SemanticsService.announce`) for a momentary event with no persistent text host.
- [ ] `flutter test test/accessibility/` passes locally.
- [ ] The change has been tab-walked once with a mouse disconnected.
- [ ] If the change touches the reading diff, region overlays, or any tab-like chip row, the corresponding VoiceOver/TalkBack script step in section 4.2 has been re-run manually at least once this release cycle.
